# Model card — BIST educational agent (Qwen 2.5 3B + LoRA, v3)

## Summary

- **Base model**: `Qwen/Qwen2.5-3B-Instruct` @ `aa8e72537993`, trained from the 4-bit checkpoint
  `unsloth/Qwen2.5-3B-Instruct-bnb-4bit` @ `2672b5888485`. Licence: Qwen Research License.
  3B instead of 7B because 7B QLoRA is marginal on a free Colab T4 (14.56 GB); same chat
  template, tokenizer and tool-call format.
- **Adapter**: LoRA rank 16, alpha 32, dropout 0.05 on q/k/v/o + MLP projections.
  `training/adapter/adapter_model.safetensors`, SHA-256
  `ad3716e908060dc87c3095d5a20ac9811f557cf293ead4f80a2497d143908e53` (matches the training record).
- **Training**: Unsloth QLoRA (4-bit nf4) on a Colab Tesla T4, 2026-11-25: 3 epochs, 60 steps,
  effective batch 16, lr 2e-4 cosine, max_len 4096, seed 17; 50 min, peak 8.79 GB.
  Train loss 0.1599, eval loss 0.0032. Full record: `training/config/hyperparams.json`.
- **Objective**: supervised fine-tuning on grounding-checked MCP tool-call conversations with
  `train_on_responses_only` loss masking; no RLHF.
- **Export / serving**: merged Q4_K_M GGUF (1.9 GB) from the same run, served by Ollama as
  `bist-qwen` via `training/Modelfile.finetuned` (temperature 0, top_p 0.9, num_ctx 16384).
  With `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0` it runs 100% on a 4 GB
  RTX 3050 laptop GPU, about 25 s per question.

## Intended use

A **teaching aid** for CSE481. It answers questions about BIST equities from cached Yahoo
prices, Fintables TMS 29 statements (THYAO) and KAP events, through 21 read-only MCP tools.
Every answer ends in one of the 8 educational labels:

`HOLD · WATCH · INVESTIGATE · POTENTIAL_CATCH_UP_CANDIDATE · TECHNICAL_REVERSAL_CANDIDATE ·
FUNDAMENTAL_IMPROVEMENT_CANDIDATE · REJECT_SIGNAL · ANALYSIS_UNSAFE`

It is meant to be run through `scripts/ask.py` / `scripts/run_presentation_scenarios.py`
(training-format tool calls, see below). Not for trading.

## Training data (dataset v3, `training/dataset/`)

- 400 conversations generated by `training/dataset/build.py`, replaying live MCP calls on
  `config/universe_live.yaml` (18 tickers, 8 sectors). Every answer figure must appear in the
  tool output shown in the same conversation, or the example is rejected (`audit.json`: 0 rejected
  for grounding).
- Answers copy the tools' precomputed blocks: `sector_summary`, the weekday `summary`,
  `best_family`, `labels_by_rule`, `publication_reaction`, and state the tool's `label_by_rule`.
- Distribution: sector 100, weekday 60, reversal 100, fundamental 50 (THYAO), analysis-unsafe /
  unavailable 90. 46% natural-language questions (English and Turkish) with the presentation
  system prompt and knowledge-base context; the rest name the tool.
- The five presentation scenarios' exact tool settings are held out (including the fundamental
  dates that share S4's statements).
- 80/20 split stratified by scenario. Tool text trimmed to 4,500 characters, the same cap the
  presentation path uses. Conversations are **without tool schemas**: tool calls are written
  as `<tool_call>{json}</tool_call>` text.

## How it must be called

Because training had no tool schemas, the presentation path sends none and parses the model's
`<tool_call>` text (`run_agent(..., tool_schemas=False)`, recorded in each trace as
`harness.tool_protocol`). When Ollama adds its 21-schema block instead, the model calls the
right tool first and then chains unrelated ones (see the eval below).

## Evaluation

### Five presentation scenarios (`outputs/presentation/traces/`)

Natural questions that never name a tool; temperature 0, seed 17.

| Scenario | Tool chosen | Label | Grounded |
|---|---|---|---|

| S2 EREGL weekday effect, 2025 | `test_weekday_pattern` | WATCH (no p < 0.10) | all |
| S3 TCELL reversals, 120 sessions | `detect_reversal_events` | TECHNICAL_REVERSAL_CANDIDATE | all |

### 20-question §30 eval (`outputs/training/base_vs_finetuned.md`)

Base for comparison: `bist-qwen-base` (Qwen 2.5 3B Instruct, same context and sampling).

| Metric | Presentation protocol: base → fine-tuned | Original (tool schemas): base → fine-tuned |
|---|---|---|
| missing required tool | 1.00 → **0.05** | 0.10 → **0.00** |
| answers with ungrounded figures | 0.35 → **0.05** | 0.00 → 0.05 |
| invalid tool call | 0.00 → 0.10 | 0.05 → 0.45 |
| label mismatch | 0.05 → 0.10 | 0.05 → 0.10 |
| unknown label token | 0.25 → 0.45 | 0.05 → 0.20 |
| advice leak / turn limit / non-empty answer | tie | tie |

On the presentation path the base never calls a tool and invents figures in 7 of 20 answers;
the fine-tune calls the planned tool in 19 of 20. With tool schemas the base is the better
agent. The chart is `outputs/training/figures/base_vs_finetuned.png`.

### A→E harness (`outputs/training/phase_g_harness_summary.md`)

Tools take evidence_coverage and workflow_completion from 0 to 1.0 for both models; the
fine-tune keeps constraint_compliance in 5 of 5 stages (base 2 of 5); numeric_exactness is 0
for both on the 11-field question.

## Limitations

- **Reads rather than reasons.** Correct conclusions depend on the tools doing the
  comparisons. In a dry run on an 8-sector output, the label was right but the explanation
  quoted another sector's figures. The grounding audit proves figures exist in tool outputs;
  it does not prove they are attached to the right ticker.
- **Over-cautious outside its five question types.** On the eval, 11 of 20 answers say
  ANALYSIS_UNSAFE where only 2 are unsafe cases; once it labelled ANALYSIS_UNSAFE although
  the gate said INVESTIGATE. It does not know tools it was not trained on (asked to call
  `project_status`, it called `check_data_quality`).
- **Works only in its own tool format** (see "How it must be called").
- **Quotes tool codes** (HARD_BLOCK, INVALID_SYMBOL), which the unknown-label metric counts.
- Fundamentals exist for THYAO only; other tickers get `available: false` and INVESTIGATE.
- No RLHF; "no investment advice" relies on the system prompt, the label set and the gate.
