# Model card — BIST educational agent (Qwen 2.5 3B + LoRA)

## Summary

- **Base model**: `unsloth/Qwen2.5-3B-Instruct-bnb-4bit` (Apache 2.0, 4-bit base checkpoint).
  Switched from 7B to 3B per the project plan's D2 fallback for <12 GB VRAM — Colab T4's
  14.56 GB is marginal for 7B QLoRA after activations + logits upcast. Same chat template,
  same tokenizer, same tool-call format, so downstream harness and evaluation code are
  unchanged.
- **Adapter**: LoRA rank 16, alpha 32, dropout 0.05 on q/k/v/o + MLP projections.
- **Training**: Unsloth QLoRA 4-bit nf4 on a free Colab T4 (~20 min for 3 epochs on ~400
  examples; final eval_loss 0.031 at step 60/60).
- **Objective**: supervised SFT on verified MCP tool-call traces with
  `train_on_responses_only` loss masking; no RLHF.
- **Export**: Unsloth `save_pretrained_gguf(..., q4_k_m)` writes a merged GGUF (adapter
  baked into base), so `training/Modelfile.finetuned` uses `FROM ./bist_lora.gguf` rather
  than the `ADAPTER` directive.
- **Deployment**: Ollama locally via `training/Modelfile.finetuned` → tag `bist-qwen`.
  Context: Ollama caps `num_ctx` at the GGUF's advertised 32k regardless of Modelfile
  override; `scripts/local_agent.py` truncates each MCP tool-result payload at 12 KB to
  keep multi-round traces under the ceiling.

## Intended use

This model is a **teaching aid** for CSE 481 (Engineering Economics). It analyses BIST
equities from frozen Fintables + TMS 29 data with strict "no investment advice"
guardrails. It cites the MCP tool each numeric claim came from and chooses one of the
8 educational labels:

`HOLD · WATCH · INVESTIGATE · POTENTIAL_CATCH_UP_CANDIDATE · TECHNICAL_REVERSAL_CANDIDATE ·
FUNDAMENTAL_IMPROVEMENT_CANDIDATE · REJECT_SIGNAL · ANALYSIS_UNSAFE`

## Training data

- 400 synthetic-but-verified examples generated by `training/dataset/build.py`.
- Each example replays live MCP tool calls; numeric fidelity is guaranteed to match the
  committed Fintables vintages to 1e-6.
- Scenario distribution (Scenario IDs from the project PDF §22):
  - Scenario 1 (sector laggards): 80 examples
  - Scenario 2 (weekday patterns): 60 examples
  - Scenario 3 (reversal events): 100 examples
  - Scenario 4 (fundamental reaction): 80 examples
  - Negative / `ANALYSIS_UNSAFE` gate cases: 80 examples
- Rejection rate and audit stats are logged to `training/dataset/audit.json`.
- 80/20 train/eval split, stratified by scenario.

## Evaluation (§30 metrics)

Measured by `training/eval/run_baseline.py` on a 20-question hand-curated eval set:

| Metric | Direction | Measured by |
|---|---|---|
| Invalid tool-call rate | Lower is better | `isError` or exception in trace |
| Missing required tool rate | Lower is better | Expected `expected_tools` vs observed |
| Label mismatch rate | Lower is better | Detected label ∉ expected set |
| Advice-leak rate | Lower is better | Banned phrases regex (`i recommend`, etc.) |
| Unknown-label rate | Lower is better | Label token ∉ 8-label whitelist |
| Reproducibility rate | Higher is better | Non-empty final answer |

Head-to-head report: `outputs/training/base_vs_finetuned.md`.

## Limitations

- Trained on 400 examples — small corpus; cannot generalise beyond the 10-ticker universe.
- **Tool-loop pathology**: On ~20 % of the eval set (q05, q06, q07, q16) the model exhausts
  the 15-turn budget by cycling through tools after its first successful call. Root cause:
  the training demonstrations include multi-tool trajectories but lack explicit stop
  signals, so the model generalizes "after a successful call, call another one" rather
  than "after a successful call, answer." See `outputs/training/base_vs_finetuned.md`
  for the per-question breakdown. First candidate for any future dataset iteration.
- Turkish economic news beyond KAP is absent; macro context is limited to cached USD/TRY; the TCMB / TÜİK reader exists, but no series are cached in this submission.
- Period mismatch (pre/post TMS 29) is hard-blocked by the gate; the model will refuse rather
  than fuse incompatible-presentation statements.
- No safety RLHF — relies entirely on the system prompt and the data-quality gate for
  compliance with "no investment advice."
- Not suitable for anything but graded coursework; must not be used for live trading.

## Reproducibility

- Base model SHA pinned via `ollama list` output; see `training/MODEL_PINS.txt` after
  a successful pull.
- LoRA adapter hash recorded at submission time in `SUBMISSION_MANIFEST.json`.
- All training data is deterministic given the committed Fintables vintages and the seed
  passed to `training/dataset/build.py`.
