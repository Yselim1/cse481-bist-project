Engineering

The Dedup Guard — Solving Tool-Loop Pathology

The Problem

The 3B model generalises: "after a successful tool call → call another."

On ~20% of eval questions, it cycles the same tool endlessly instead of writing an answer.

QuestionCalls beforeCalls after
q06 (rank_sector loop)15 identical2
q07 (rank_sector loop)14+ mixed2
q16 (backtest + signal)20+3
q09 (weekday loop)10 identical8 (partial)

The Fix

At inference time in scripts/local_agent.py:

  • Track seen_calls set: tool_name:json(args)
  • On first repeat call: return dedup_note (not error), disable tools immediately
  • Inject "write your final answer now" nudge
  • Safety net: force answer after turn 10

Key: returns {"dedup_note": "..."} not {"error": "..."} — evaluator does not count this as an MCP failure.

Limitations

Honest Limitations

1. Small Training Corpus

400 examples — cannot generalise beyond the 10-ticker universe. First candidate for improvement: add more gate_unsafe examples for unknown tickers and future dates.

2. Gate-Unsafe Knowledge Gap

Model does not reliably call check_data_quality first for unknown tickers or future dates (q17, q18, q19 fail). Root cause: not enough negative examples in training set.

3. Metric-Key Vocabulary Artifact

Fine-tune quotes domain identifiers from tool outputs verbatim. Evaluator regex catches them as "unknown labels" — test-design gap, not actual violations.

4. Numeric Schema Slots

Model writes rich narratives but does not populate strict numeric output fields (revenue, net profit, four strategy returns). Under-trained on scalar extraction into structured schemas.

5. No RLHF

"No investment advice" compliance relies entirely on the SYSTEM_PROMPT and data-quality gate — no reinforcement-learning alignment.

6. TMS29 Boundary

Pre/post-TMS29 statements cannot be mixed. The gate hard-blocks PERIOD_MISMATCH — model refuses rather than fusing incompatible data. Appropriate, but limits historical depth.

Demo

Live Demo — Two Harnesses

The project runs two distinct processes. One does work, the other measures it.

1. Agent Harness — the model doing work

LLM + MCP tools in a Claude-Code-style loop. One question in, tool calls fire, one grounded answer out.

Smoke: python scripts/local_agent.py --smoke --model bist-qwen

→ One project_status call, ~30 s, proves the wiring works.

Real question:
python scripts/local_agent.py --ticker THYAO.IS --as-of 2025-12-31 --model bist-qwen

→ 3–6 tool calls · one of 8 educational labels · trace in outputs/agent/

2. Evaluation Harness — measuring the architecture

Runs the same fixed question through the five A→E stages and scores each one. Produces the comparison in slide 9.

Command:
python scripts/run_harness_experiments.py
  --backend ollama --model bist-qwen

→ 5 stages × ~2 min each ≈ 8–15 min total · writes outputs/harness/comparison.json + per-stage scores.

Pre-run before the talk; show comparison.base.json vs comparison.finetuned.json live.

One-shot launcher

.\scripts\presentation_launch.ps1

Opens 4 PowerShell windows — ollama serve, health check, agent smoke, 5-stage harness — so each step can be inspected independently. Flags: -Model qwen2.5:7b-instruct, -SkipHarness.
